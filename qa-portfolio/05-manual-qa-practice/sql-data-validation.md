# 03. SQL-проверки качества данных интернет-магазина

## Цель

Показать, как QA использует SQL для проверки данных после действий пользователя: регистрации, оформления заказа и изменения статусов.

**Среда:** PostgreSQL или SQLite с учебной БД интернет-магазина. SQL-запросы не привязаны к production-данным и не содержат персональной информации.

## Модель данных

| Таблица | Назначение |
| --- | --- |
| `users` | учётные записи покупателей |
| `products` | каталог товаров |
| `orders` | заказы и их статусы |
| `order_items` | состав каждого заказа |

## Проверки

| ID | Проверка | Риск |
| --- | --- | --- |
| SQL-001 | поиск заказов без пользователя | нарушена ссылочная целостность |
| SQL-002 | поиск позиций заказа без заказа | «висячие» записи |
| SQL-003 | заказы с отрицательной или нулевой суммой | ошибка расчёта стоимости |
| SQL-004 | дублирующиеся email | проблема регистрации/уникальности |
| SQL-005 | заказы с неизвестным статусом | некорректный бизнес-процесс |
| SQL-006 | сверка суммы заказа с позициями | расхождение UI/API и БД |

## Запросы

Смотри файл [`validation_queries.sql`](validation_queries.sql). Перед запуском названия полей адаптируются под фактическую схему базы.

## Как проверять результат

Запросы рассчитаны на схему из раздела «Модель данных», которую нужно подготовить отдельно: эта папка содержит **примеры SQL-проверок**, а не готовую базу и не отчёт о реальном прогоне. Для воспроизводимого примера с готовой SQLite-базой и автотестами см. [проект заказов](../06-order-data-tests/README.md).

## Что демонстрирует проект

Связь функционального тестирования с данными: QA не ограничивается интерфейсом, а умеет проверять сохранение, целостность и согласованность информации.
