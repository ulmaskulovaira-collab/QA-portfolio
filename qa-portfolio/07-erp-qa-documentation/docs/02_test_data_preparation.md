# Подготовка тестовых данных

## Зачем это нужно

В ERP-системах многие сценарии нельзя корректно проверить без заранее подготовленных данных. Если сразу идти в интерфейс, можно попасть в пустой список, не увидеть нужную кнопку или принять отсутствие данных за ошибку функциональности.

Поэтому перед проверкой я сначала анализирую предусловия.

## Что я проверяю перед тестом

| Что проверить | Зачем |
| --- | --- |
| Пользователь | Чтобы сценарий выполнялся от нужного типа пользователя |
| Роль | Чтобы проверить доступы и ограничения |
| Доступ к разделу | Чтобы отделить ошибку прав от ошибки функциональности |
| Тестовый объект | Чтобы не проверять пустой интерфейс |
| Статус объекта | Чтобы действие было доступно по условиям сценария |
| Связанные записи | Чтобы проверить процесс целиком |
| Остатки или количество | Чтобы проверить ограничения и изменения после действия |
| История операций | Чтобы подтвердить, что действие сохранилось |
| Окружение | Чтобы исключить проблему запуска, сборки или стенда |

## Пример логики подготовки

Перед проверкой рабочего сценария я задаю себе вопросы:

1. Кто выполняет действие?
2. Есть ли у пользователя нужная роль?
3. Видит ли пользователь нужный раздел?
4. Есть ли объект, с которым можно работать?
5. Подходит ли статус объекта?
6. Есть ли связанные данные?
7. Что должно измениться после действия?
8. Где можно проверить результат?

## Пример чек-листа предусловий

| № | Предусловие | Статус |
| ---: | --- | --- |
| 1 | Тестовый пользователь создан | Не проверено |
| 2 | Пользователю назначена нужная роль | Не проверено |
| 3 | Раздел доступен пользователю | Не проверено |
| 4 | Есть тестовый объект | Не проверено |
| 5 | Статус объекта подходит для проверки | Не проверено |
| 6 | Есть связанные данные | Не проверено |
| 7 | Есть место, где можно сверить результат | Не проверено |

## Вывод

Такой подход помогает быстрее понять, что именно проверяется: функциональность, права доступа, данные или состояние окружения.
